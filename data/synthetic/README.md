# Синтетичний held-out набір (200 повідомлень)

Відповідь на зауваження наукового керівника: 35 повідомлень
`data/test_messages.json` для висновків замало. Тут 200 українських
повідомлень із **повним еталоном на рівні полів**, а не лише на рівні
«подія є / події немає».

Набір побудовано **«спершу еталон, потім текст»**: параметри події
(тип, дата, час, місце, організатор, аудиторія) насемпльовано випадково з
фіксованим сідом, дати пораховано правилами 1–7 системного промта, і тільки
після цього LLM (Claude — **не** та, що тестується) написала повідомлення
навколо готового запису. Тому еталон не «вгадується з тексту постфактум»:
він первинний.

## Що тут лежить

| файл | що це |
|---|---|
| `synthetic_messages.json` | сам набір: 200 об'єктів, id 3001–3200 |
| `audit_sample_2.md` | ручний аудит вибірки (15 повідомлень) |
| `generation_sources.zip` | походження: скрипти й проміжні дані генерації |
| `corrections.json` | правки еталона після ручного розгляду (може бути відсутнім) |

> `audit_sample.md` (аудит на 25 повідомлень) у переданих файлах був відсутній —
> у теці лише `audit_sample_2.md`. Якщо перший аудит існує, його місце тут.

## Склад

200 = **118 анонсів** (88 однособутійних, 18 багатоподійних, 6 перенесень,
6 масових консультацій) + **70 пасток** (13 підтипів) + **12 індивідуальних
консультацій**. Еталонних подій 152, з них 140 в анонсах → **1540 полів**
(140 × 11) — це знаменник головної метрики.

Дві сотні згенеровано різними сідами й пулами тем: 3001–3100 (сід 20260921)
і 3101–3200 (сід 20260922, більше багатоподійних, перенесень і консультацій).
Звіт рахує метрики для половин окремо — великий розрив означав би, що
результат залежить від генератора, а не від моделі.

## Формат запису

```json
{
  "source_message_id": 3043,
  "date": "2026-10-12",              // дата публікації = опорна дата для моделі
  "source_channel": "@synthetic_faculty",
  "text": "…",
  "_expect": "1 подія: …",           // угода data/test_messages.json
  "gold": {
    "kind": "announcement | trap | individual",
    "category": "single | multi:<kind> | postponed | trap:<subtype> | …",
    "tags": ["relative:next_weekday", "online", "boundary", …],
    "reaches_db": true,
    "events": [ { /* 11 полів схеми, кожне об'єктом */ } ]
  }
}
```

`keys` у полі — це список груп: значення зараховується, якщо КОЖНА група
має хоч ОДНУ альтернативу-підрядок у нормалізованому значенні (І з АБО).
Так «студенти 2-го курсу» закриває ключ «2 курс», а «Zoom» — еталонне
«Онлайн (Zoom)».

## Угоди розмітки — це рішення, а не недогляд

1. **Дати** рахуються за правилами 1–7 промта відносно `date`. «цього
   четверга» і «у найближчу суботу» — правило 3; «наступної п'ятниці» —
   правило 4. П'ять повідомлень мають тег `ambiguous:next_weekday`, бо
   повідомлення 211 реального набору читає цю конструкцію інакше; метрики
   звітуються і з ними, і без них.
2. **Дедлайни — не події.** В 11 анонсах з тегом `deadline_mention` дедлайн
   реєстрації належить до `description`; окрема подія «дедлайн» рахується як
   зайва. Повідомлення, де є ЛИШЕ дедлайн, — пастка.
3. **`boundary`-пастки** (4 дедлайни, 4 зміни іспиту, 2 графіки захистів)
   мають `events: []` за угодою календаря факультету. Вони завжди виносяться
   окремим рядком, щоб головна метрика пасток не залежала від спірної угоди.
4. **Індивідуальні консультації** мають подію в еталоні (модель може і має
   право її видобути), але `reaches_db: false`: відсікає їх детермінований
   `app/services/audience.py`, а не модель.
5. **Доповідачі й компанії-учасники — не організатори.** Де текст організатора
   не називає, еталон null.
6. **Перенесення** (`postponed`) тримають у еталоні НОВУ дату або час; стара —
   відволікач.

## Перевірка набору

```powershell
python -m scripts.synthetic.check_synthetic data\synthetic\synthetic_messages.json
# 200 повідомлень {'announcement': 118, 'trap': 70, 'individual': 12},
# еталонних подій 152, помилок 0
```

Перевірка детермінована й без моделі: перераховує кожну дату з фрази в тексті,
шукає в тексті фрази часу, посилання, коди зустрічі й ключі всіх полів.

## Правки еталона

Датасет **не редагується руками**. Після ручного розгляду (`review.md`)
правки кладуться в `corrections.json`:

```json
{ "3043": { "events[0].date.value": "2026-10-19", "reason": "чому" } }
```

Вони накладаються під час завантаження і оцінювачем, і перевіркою:

```powershell
python -m scripts.synthetic.check_synthetic data\synthetic\synthetic_messages.json `
    --corrections data\synthetic\corrections.json
```

Виправлений набір зобов'язаний лишатися валідним — інакше правка тихо
зіпсувала б розмітку.

## ⚠ Набір held-out

Ці повідомлення **не можна** використовувати як few-shot і **не можна** під
них підганяти промт. Кожен звіт містить `prompt_sha256`; якщо промт змінився,
числа треба перерахувати й позначити новим відбитком. Результати на цьому
наборі **ніколи не змішуються** з результатами на `data/test_messages.json` —
це різні набори й різні знаменники.
